# Маршрутизация: реализация и проверки

`/settings/routing` использует существующий HomeShell с активным родительским пунктом «Настройки». `routing.css` ограничен `.workspace-routing`, использует общие токены без изменения их значений: Sidebar #0A1427, белые/тёмные поверхности, красные действия, компактная таблица, читаемые подписи и скруглённый диалог. Завершённые разделы не получили новых стилей. Таблица на мобильных прокручивается горизонтально, диалог имеет естественную вертикальную прокрутку.

Сохранены список и пагинация по 20 правил, создание, редактирование, активность, категория, область подразделения/глобальная и исполнитель. Новые условия назначения, поиск, фильтры и удаление не добавлялись. Приоритет и ограничения алгоритма объяснены на странице и в редакторе. Флаг активности не выдаётся за гарантию фактического назначения.

Редактор вынесен из ветки маршрутизации AdminDirectory в `routing-editor.tsx`. Он получает уже загруженные справочники от родителя, не дублирует запросы и не влияет на формы остальных справочников. EMPLOYEE/MANAGER не получают интерфейс управления или запросы справочников этой страницы; canViewCompanyAnalytics не меняет это ограничение. Серверные проверки сохранены.

## Сохранение области и идентификаторов

Выбор категории, подразделения, исполнителя и активности хранится в управляемом React-состоянии, инициализированном исходным RoutingDto. Отсутствующее в первых 100 записях значение получает отдельный option с тем же ID и честной подписью. Пропажа записи при повторной загрузке не меняет выбранный ID. Отсутствующее подразделение не заменяется пустой строкой/global. Глобальное правило отправляется только при изначально глобальной области либо явном выборе пользователя.

PATCH содержит только изменённые поля, поэтому статусный PATCH не передаёт и не заменяет исходные связи. Для создания отправляются все прежние обязательные поля. До сохранения проверяются доступность справочников и выбранных записей, роль исполнителя, а для активного правила также активность категории, подразделения, исполнителя и его подразделения. Если подтверждение невозможно, кнопка и обработчик блокируют отправку с объяснением. Неполные справочники явно показывают загруженное и общее число; полный список не имитируется.

Это намеренно консервативное ограничение: при отсутствии выбранной записи в загруженном списке редактирование не сохраняется до появления достоверных данных или явного выбора доступной записи. Подгрузка всех страниц или новый поиск не добавлялись. Невозможность сохранить не приводит к молчаливой смене области.

## Ошибки и повтор

Список правил разделяет загрузку, ошибку с повтором GET и пустые данные. Каждый справочник в диалоге имеет собственную загрузку/ошибку/повтор, также доступно обновление всех справочников. При их загрузке или ошибке сохранение запрещено. Ввод сохраняется после сетевых ошибок и отказов API. Ошибки полей связаны через aria-describedby/aria-invalid; первый ошибочный контрол получает фокус. 409 CONFLICT объясняет наличие активного правила для категории и области. INVALID_ROUTING обновляет справочники, сохраняя выбор. Ref предотвращает двойную отправку; неизменённое правило не отправляет пустой PATCH.

## Проверки

Typecheck, lint, 590 тестов и build прошли. В обеих темах DOM-тесты проверяют роли, список/пагинацию, создание, частичные PATCH, ошибки/повтор, конфликты, неактивные связи, лимиты справочников, двойную отправку и отмену диалога. Отдельные тесты подтверждают: отсутствие подразделения в списке не превращает его в global; все исходные ID сохраняются при пустых/ошибочных справочниках; восстановление справочников позволяет отправить только изменение активности; переход к global требует явного выбора; смена категории не меняет область.

Неизменённые обработчики и saveRule проверены с подменённой БД на ADMIN-only, сохранение исходных связей при статусном PATCH, явный global, недопустимые связи и преобразование P2002 в 409. У resolveAssignee проверены локальный приоритет, fallback к global, null при отсутствии правил и параметры запроса, исключающие автора, неактивного исполнителя и неактивное подразделение исполнителя. Проверено отсутствие операций переназначения обращений при сохранении правила. Это контрактные проверки вызовов, а не реальный SQL-прогон.

Регрессионные тесты сотрудников, категорий, подразделений и ранее завершённых страниц прошли. Отдельный тест маршрутизации в `directory-regression.test.tsx` обновлён для управляемых select и достоверных полей активности исполнителя. Backend, API, авторизация, PostgreSQL, алгоритм назначения и миграции не изменены; реальные правила и обращения не менялись.

HTTP: `/`, `/settings/routing`, `/settings/categories`, `/settings/departments`, `/team` — 200; `/api/v1/health` — 200, database connected. Эти проверки не подтверждают реальные операции под разными аккаунтами. Build выдал прежнее предупреждение о внешнем lock-файле в D:\Projects, но завершился успешно.

## Сохранившиеся серверные ограничения

- Если исполнитель стал EMPLOYEE, существующий saveRule может отказать даже в отключении правила: роль MANAGER/ADMIN требуется независимо от активности правила. UI объясняет эту причину, серверное поведение не исправлялось.
- Версия правила не проверяется: параллельные изменения всё ещё могут перезаписывать друг друга. Частичный PATCH сокращает объём отправки, но не заменяет серверный контроль версий.
- Миграция содержит частичные уникальные индексы активного локального и глобального правил. Их фактическое наличие и действие в production-БД нужно проверить отдельно; это не сделано в текущем этапе.

## Неподтверждённые сценарии

Браузерный сервис недоступен (`The browser access host is unavailable`). Не подтверждены скриншот и геометрия обеих тем/мобильного окна, реальные Tab/Shift+Tab/Escape и фокус-ловушка/возврат фокуса диалога, визуальное сравнение остальных справочников, операции под настоящими ролями, реальные назначения и конкурентные конфликты с PostgreSQL. Пределы первых 100 записей остаются; UI явно обозначает их и блокирует недостоверное сохранение.

Файлы этапа: `admin-directory.tsx`, новый `routing-editor.tsx`, маршрут в `app-frame.tsx`, класс HomeShell, область общих токенов `tickets.css`, импорт `layout.tsx`, новый `routing.css`; тесты `routing-ui.test.tsx`, `routing-contract.test.ts`, обновлённые проверки оболочки и справочников. Push и deployment не выполнялись.
