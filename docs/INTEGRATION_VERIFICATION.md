В начало существующего `.postgres/data/pg_hba.conf` добавлен только блок новой тестовой роли:

```text
host modus_link_hackathon_20261113_test modus_link_hackathon_test 127.0.0.1/32 scram-sha-256
host all modus_link_hackathon_test 0.0.0.0/0 reject
host all modus_link_hackathon_test ::/0 reject
local all modus_link_hackathon_test reject
host replication modus_link_hackathon_test 0.0.0.0/0 reject
host replication modus_link_hackathon_test ::/0 reject
local replication modus_link_hackathon_test reject
```

Разрешающее правило идёт первым, затем запреты этой роли, затем исходные общие правила. Отдельные replication-запреты нужны, поскольку DATABASE=all не включает физические replication-подключения. Кроме того, роль имеет NOREPLICATION.

Все байты первоначального HBA сохранены после добавленного блока; это проверено SHA-256. Разобранные исходные шесть правил также сравнены до/после и не изменились, кроме номеров строк/позиций. Все новые правила адресованы только точному имени новой роли.

Выполнен `SELECT pg_reload_conf()`, результат true. `pg_hba_file_rules` показывает 13 правил (7 новых + 6 исходных), ни у одного нет error. Время `pg_postmaster_start_time()` до и после совпадает: PostgreSQL не перезапускался. Для hba_file, listen_addresses и port нет pending_restart.

Ошибок проверки или риска для существующих подключений не обнаружено; восстановление резервной копии не потребовалось.

## Подключения и права

Перед изменяющими SQL-операциями проверялись фактические current_database(), inet_server_addr() и inet_server_port(). Для операций создания роли/БД использовано административное подключение к существующему локальному серверу `127.0.0.1:55432`; изменение ACL и схемы выполнялось только внутри новой тестовой БД. Подтверждён data_directory существующего кластера `.postgres/data`.

| Реальное подключение новой ролью | Результат |
| --- | --- |
| modus_link_hackathon_20261113_test, 127.0.0.1:55432 | Успешно; SELECT 1 = 1, current_database совпадает, is_superuser=off |
| modus_pulse, тот же адрес | Отказ SQLSTATE 28000, pg_hba.conf rejects connection |
| modus_pulse_test, тот же адрес | Отказ SQLSTATE 28000, pg_hba.conf rejects connection |
| postgres, тот же адрес | Отказ SQLSTATE 28000, pg_hba.conf rejects connection |

Пароль новой роли сгенерирован криптографически и не выводился. Роль имеет NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOINHERIT, NOREPLICATION, NOBYPASSRLS; членство в других ролях отсутствует. Лимит подключений — 12.

Новая БД принадлежит существующей административной роли, а не runtime-роли. В новой БД отозваны права PUBLIC на БД и схему public; runtime выданы только CONNECT к новой БД и USAGE схемы public. Проверено: CREATE DATABASE/schema, CREATE в public и TEMP не доступны. Пользовательских таблиц в новой БД — **0**.

Роль пока может подключаться и выполнять SELECT 1, но приложение с таблицами ещё не подготовлено. После отдельно разрешённого применения миграций потребуется выдать runtime необходимые DML/sequence-права **только в новой БД**. Миграции не должны выполняться runtime-ролью; superuser не используется для подключения тестового приложения.

### Основная БД

- ACL `modus_pulse` и `modus_pulse_test` до/после совпадают (datacl=NULL); их права не изменялись.
- ACL-проверка CONNECT основной БД по-прежнему возвращает true через PUBLIC. Фактическое подключение новой роли блокируется **HBA**, а не отзывом этого ACL-права.
- USAGE схемы public основной БД наследуется через PUBLIC; CREATE отсутствует.
- Новая роль не имеет ни одного из проверенных табличных прав SELECT/INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER на всех **11** таблицах/представлениях основной public-схемы.
- Проверены также отсутствие административных флагов и членств. Таким образом, runtime не имеет данных основного приложения и не может обойти HBA сменой привилегированной роли.

### IPv6 и локальные сокеты

IPv6, Unix-domain local и replication-запреты проверены по порядку и результатам pg_hba_file_rules. Сервер сейчас слушает только `127.0.0.1`; listen_addresses не менялся. Поэтому реальное прохождение HBA по IPv6/Unix-сокету в текущем Windows-окружении **не проверено**. Отсутствие IPv6 listener не выдаётся за проверенный отказ HBA. Реальные разрешения/отказы выше проверены по рабочему IPv4-подключению.

## Что остаётся перед интеграционным прогоном

1. На следующем подтверждённом этапе применить существующие миграции только к новой БД после повторной идентификации подключения.
2. Выдать runtime минимальные права на созданные таблицы и sequence только новой БД, затем подготовить синтетические данные.
3. Подготовить явный запуск на 3100 с отдельным env и остановкой только тестового процесса.
4. Не запускать существующий integration runner без учёта ограничений: он подключается к служебной postgres, автоматически применяет миграции, а suite содержит loginThrottle.deleteMany(). Новая runtime-роль намеренно не может выполнять административную подготовку. Массовую очистку запускать нельзя без отдельного согласования; бизнес-логику приложения при этом менять не требуется.
5. Проверить полный сценарий и отрицательные случаи реальным HTTP/PostgreSQL, затем отдельно браузером; до и после повторить read-only контроль основной БД. Не использовать старую modus_pulse_test.
6. Не удалять новую БД/роль и тестовые записи автоматически.

Прежний блокер HBA-изоляции снят для фактических локальных IPv4-подключений. Полная готовность демонстрации остаётся неподтверждённой до интеграционной и браузерной репетиции.
