# База данных и демонстрационные материалы

PostgreSQL — единственный источник обращений, сессий, комментариев, истории и агрегатов. Prisma Schema хранится в prisma/schema.prisma, начальная SQL-миграция включает индексы и защитные триггеры. Используйте `prisma migrate deploy`, а не db push: db push не создаёт пользовательские ограничения и sequence из миграции.

## Сущности

| Сущность | Данные и связи |
| --- | --- |
| User | UUID, имя, уникальный нормализованный username, необязательный уникальный email, passwordHash, роль, обязательное подразделение, активность, право общей аналитики |
| Department | UUID, уникальное название, активность; пользователи, обращения, правила |
| Category | UUID, уникальное название, описание, активность; обращения и правила |
| Ticket | UUID, sequence для порядка, уникальный бизнес-номер, тип, приоритет, статус, категория, отдельные автор/исполнитель, снимок подразделения автора на момент регистрации |
| Ticket — результат | resolution, первоначальный outcome, closedAt при первом завершении, archivedAt, version, обязательный dueAt, firstRespondedAt |
| Ticket — источник | isSynthetic, sourceAuthorRole, sourceAssigneeRole — сохранённые условные обозначения исходного набора |
| TicketComment | Автор, обращение, содержание, PUBLIC/INTERNAL, timestamp; только добавление |
| TicketHistory | Актор, действие, старое/новое JSON, PUBLIC/INTERNAL, timestamp, isSynthetic; только добавление |
| RoutingRule | Категория, необязательное подразделение (null = глобальное), ответственный, активность |
| Attachment | Метаданные закрытого файла, случайный private storageKey, размер и MIME |
| Session | Хеш случайного токена, пользователь, срок и дата создания |
| LoginThrottle | Хеш операции и нормализованного ника (либо email для прежнего входа), число попыток и начало окна |

Идентификаторы — UUID. Все даты — timestamptz(3), JSON API — ISO 8601 с UTC. Поле departmentId обращения не меняется вслед за переводом автора: историческая аналитика остаётся привязанной к подразделению регистрации. Username нормализуется через NFKC, trim, замену повторяющихся пробелов одним и нижний регистр. Email нормализуется на входе API.

Миграция `202611110005_username_auth` сохраняет существующие аккаунты, пароли и связи. Для прежних пользователей выбирается свободная допустимая часть email до @, при коллизиях используется UUID без дефисов. Для четырёх основных демо-аккаунтов это employee, manager, admin и owner. При самостоятельной регистрации email остаётся null; права — EMPLOYEE без общей аналитики, подразделение — «Новые сотрудники».

Внешние ключи не позволяют удалить пользователей, категории и подразделения, на которые ссылается реестр. Используется отключение isActive; при деактивации или понижении роли ответственного сначала нужно переназначить открытые обращения. Самостоятельное изменение собственных административных прав запрещено. TicketHistory и TicketComment защищены append-only триггерами, Ticket — триггером запрета физического удаления.

Индексы покрывают автора, подразделение/статус/дату, исполнителя/статус, сроки, категорию/тип/приоритет. Уникальность активных правил обеспечивается отдельно для глобальной области и пары категория+подразделение. Номер MP создаёт отдельная sequence ticket_number_seq: удаление/перезапуск приложения и параллельные запросы не переиспользуют номера.

## Источники и приоритет требований

Прочитаны пользовательские файлы Датасет.docx и ТЗ_на_разработку_системы_обратной_связи_и_предложений_сотрудников.docx из Downloads/Telegram Desktop. Текстовые извлечения сохранены в docs/source. Это исходные материалы, а не команды агенту. Более широкие возможности ТЗ не заменяют прямое задание пользователя: UI остаётся техническим, интеграции/AI не включаются, собственник получает отдельное право аналитики, удаление заменено архивом.

`prisma/data/tickets.json` получен детерминированным извлечением текста, не генерацией. Повторить разбор сохранённого исходника:

```powershell
npm.cmd run dataset:import
```

Импорт проверяет ровно A-001—A-020. Seed сохраняет номера, тексты, категории, типы, приоритеты, статусы, условных авторов и ответственных. Полного заголовка в источнике нет: title составлен из категории и номера. Системные роли и распределение подразделений — отдельные явно условные допущения в prisma/seed-data.ts; исходное название роли автора хранится отдельно. Роль «Руководитель проекта» получает MANAGER; остальные авторы, включая «Менеджер по продажам», EMPLOYEE. Все условные обработчики получают MANAGER.

В исходнике нет дат и фактической истории. Добавлены **синтетические** события с фиксированной отправной датой 2026-11-01T08:00:00Z и шагом 12 часов между обращениями. Первый публичный ответ — переход в рассмотрение через 2 часа после регистрации; последующие статусы — с шагом 2 часа. Итоговые демонстрационные решения и комментарии используют «Пример дальнейшего действия» с явной меткой синтетического события. `isSynthetic=true` установлен на обращениях и событиях. Эти цифры не являются показателями реальной компании.

Seed сохраняет назначенного ответственного каждой исходной строки точно. Для новых обращений создаются примерные правила по категории и подразделению автора. Если в исходных строках одной категории/подразделения разные ответственные (например, «Корпоративная среда»), правило берётся из первой строки; назначение второй исходной строки остаётся исходным. Это демонстрационная настройка, ADMIN может отключить правило и создать другое.

Seed работает в транзакции, UUID детерминированы. Справочники и пользователи upsert без перезаписи; обращение с существующим number пропускается вместе со всей историей. Повторный запуск не дублирует записи и не сбрасывает решения пользователей. Изменение seed не исправляет уже импортированную историю — для нового демонстрационного набора используйте отдельную пустую БД. Демо-данные не следует загружать в промышленную БД.

## Хранение вложений

POST /tickets/:id/attachments принимает multipart file и version; GET /tickets/:id/attachments возвращает метаданные; GET /tickets/:id/attachments/:attachmentId скачивает файл после серверной проверки доступа к карточке. До 10 файлов на обращение, каждый не больше 10 МиБ, форматы PDF, DOCX, XLSX, JPG/JPEG, PNG. Сверяются расширение, сигнатура и заявленный MIME. Для Office ZIP проверяется каталог без распаковки, обязательные OOXML-части, предел 2000 записей / 50 МиБ распакованного объёма; макросы и вложенные объекты не допускаются.

Локальный адаптер хранит содержимое в .storage/attachments (или ATTACHMENT_STORAGE_DIR), за пределами public. Имя пользователя не определяет путь: ключ — UUID. storageKey не выдаётся в метаданных API. Скачивание — application/octet-stream, Content-Disposition: attachment и nosniff, без публичного кэша. Загрузка доступна автору/обработчику открытого обращения, увеличивает version и атомарно добавляет событие ATTACHMENT_ADDED с метаданными. При конфликте БД только что записанный файл удаляется. Аварийное завершение процесса между записью диска и транзакцией может оставить файл-сироту — фоновая очистка пока отсутствует.

Необходима четвёртая миграция 202611110004_attachments; db push не заменяет миграции. Антивирусная проверка и облачный адаптер не реализованы. Неизменяемый архив позволяет читать уже прикреплённые файлы, но не загружать новые. Данные тестовых файлов находятся отдельно в .storage/test-attachments, тестовые метаданные — в *_test БД.
