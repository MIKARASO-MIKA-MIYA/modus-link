# Категории: реализация и проверки

`/settings/categories` подключён к существующему HomeShell с активным пунктом «Категории». Палитра мигрированных разделов используется без изменения её значений: Sidebar #0A1427, белые/тёмные поверхности, красные действия. Новые правила `categories.css` ограничены `.workspace-categories`. Ранее завершённые страницы не получили новых стилей.

Сохранены список, поля названия/описания/активности, создание, PATCH-редактирование и пагинация по 20 записей. Удаление, поиск и фильтры не добавлены. Компактная таблица имеет читаемые статусы и перенос длинного текста; на мобильных доступна горизонтальная прокрутка. Диалог сохраняет нативное поведение Modal, доступные подписи и естественную прокрутку; основной текст от 14 px, подсказки от 12 px, мобильные поля 16 px.

Раздел назван «Категории». Сроки 2/5/10 дней сохранены как справочная информация с явным пояснением, что на этой странице они не редактируются. Подсказка активности объясняет, что деактивация ограничивает новые обращения и сохраняет существующие.

В ветке категорий убран запрос подразделений и его повтор после сохранения. Начальная и повторная загрузки показывают загрузчик; при ошибке есть безопасный повтор, пустой список отображается только без ошибки/загрузки. Клиентская проверка названия 2–120 символов и необязательного описания до 1000 символов соответствует серверным ограничениям; крайние пробелы обрезаются в отправляемых значениях, пустое описание отправляется как null. Ошибки API и конфликта названия показываются у полей, связаны через aria-describedby/aria-invalid; первое ошибочное поле получает фокус. Ввод сохраняется при отказе API. Ref блокирует повторную отправку до перерисовки React.

Изменения AdminDirectory ограничены веткой категорий либо переиспользуют существующее отображение ошибок сотрудников с сохранением прежних user-ID атрибутов. Подразделения и маршрутизация сохраняют Fragment-контейнер и прежние формы. Их отдельные регрессионные тесты проверяют структуру и POST-поля. Существующие тесты сотрудников и остальных страниц также прошли. Это проверка DOM и поведения, не визуальное утверждение.

Файлы этапа: `admin-directory.tsx`, маршрутизация `app-frame.tsx`, класс `home-shell.tsx`, область общих токенов `tickets.css`, импорт `layout.tsx`; добавлен `categories.css`. Тесты: обновлён `auth-ui.test.tsx`; добавлены `categories-ui.test.tsx`, `categories-contract.test.ts`, `directory-regression.test.tsx`.

Проверки: typecheck, lint, 474 теста и build прошли. Категории проверены в обеих темах на права, создание/редактирование/деактивацию, граничную валидацию, ошибки сети/API, конфликты, сохранение текста, повтор, двойную отправку, пагинацию, доступные поля и отмену диалога.

Контрактные тесты вызывают неизменённые серверные обработчики с подменённой БД: EMPLOYEE/MANAGER получают 403 на POST/PATCH, ADMIN создаёт и деактивирует категорию. После деактивации существующий getTicket остаётся доступным; createTicket отклоняет неактивную категорию с INACTIVE_CATEGORY до создания новой записи. Категории для EMPLOYEE/MANAGER отбираются по isActive=true, ADMIN видит также неактивные. Тесты подтверждают отсутствие вызовов изменения/удаления обращений при этом сценарии. Реальная БД и реальные категории/обращения не изменялись; это не прогон с настоящим PostgreSQL.

HTTP-проверки локального сервера: `/`, `/settings/categories`, `/team`, `/settings/departments`, `/settings/routing` возвращают 200; `/api/v1/health` — 200, database connected. Проверки HTML-маршрутов не подтверждают загрузку записей под реальными аккаунтами.

Браузерный сервис недоступен (`The browser access host is unavailable`). Скриншот, реальная Tab-навигация и фокус-ловушка диалога, визуальная адаптивность и сравнение других страниц остаются открытыми. Build завершился с прежним предупреждением о внешнем lock-файле в D:\Projects. Backend, API, авторизация, PostgreSQL, структура БД и миграции не изменены; push и deployment не выполнялись.
